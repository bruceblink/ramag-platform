# Ramag Platform 主线路线：维护收尾与插件化

> 状态：现行路线
> 更新日期：2026-10-27
> 执行入口：[01-development-plan.md](01-development-plan.md)
> 插件接口设计：[04-plugin-platform-roadmap.md](04-plugin-platform-roadmap.md)

## 1. 路线结论

Ramag 保留当前原生工具和基础设施，移除本机协作与 JSON Path 提取器。当前主线继续完成已排期的
维护、UI、连接工作区回归和发布任务。用户已指定：当前主线完成后，以插件平台化作为新的开发主线。

`it-tools-template` 继续独立承担自己的 Web、PWA、Electron 和通用工具工作台。两个项目可以提供相同
场景的不同实现，但不共享进程、代码依赖、接口协议或发布物。

## 3. 后续主线：插件平台化

现有 `ToolRegistry`、`StaticPluginHost`、插件描述、生命周期、能力权限、设置、目录和任务预算构成静态
插件基线。后续工作先收敛平台与插件的接口，再用试点插件验证开发流程，最后逐步把保留的业务能力放入
插件模块。插件路线详见[插件平台路线图](04-plugin-platform-roadmap.md)。

| 顺序 | ID | 工作 | 验收条件 |
|---|---|---|---|
| 后主线 1 | `RAMAG-PLUGIN-DESIGN-001` | 盘点静态插件基线，设计插件接口、贡献点和平台/插件责任边界；比较静态内置、WASM、运行时动态加载和进程外插件等承载方式 | 形成版本兼容、权限、生命周期、设置与秘密、任务取消、资源上限、诊断和分发决策；给出接口规范与开发样例 |
| 后主线 2 | `RAMAG-PLUGIN-PILOT-001` | 从现有工具中选择一个低风险能力，按已评审接口完成试点插件和开发流程 | 注册、入口显示、生命周期、设置、授权、错误恢复和卸载通过验收；保留原有用户行为和数据 |
| 后主线 3 | `RAMAG-PLUGIN-MIGRATE-001` | 分批将保留的工具收敛为插件模块，减少业务功能对主程序组合根和宿主内部结构的依赖 | 每批独立验证、交付和回滚；既有协议、数据、凭据和工具顺序保持兼容 |

插件接口冻结后，所有新增业务功能都以插件模块交付。平台核心只负责跨插件共用的窗口、注册、生命周期、
授权、设置、任务和 UI 宿主服务。业务工具不得直接加入核心 crate 或绕过插件 API 接入 Shell。

## 4. 插件路线的决策边界

- 当前插件实现是编译进主程序的静态 Rust 插件。动态加载、WASM 执行和进程外 IPC 都是待评估选项，接口设计阶段必须记录选择理由、兼容要求和运行边界。
- 本路线允许设计插件接口、开发第一方试点插件并逐步迁移保留功能。它不自动批准第三方不受信任代码、插件市场、远程执行、自动更新或跨语言 ABI。
- 若选择运行时加载外部插件，必须先完成来源验证、签名、权限审批、隔离、崩溃恢复、兼容检查、安装回滚和清理设计。
- 插件化不改变桌面端使用 Rust/GPUI 的既定方向。插件不能直接访问宿主内部状态；它们通过版本化接口和最小权限调用平台能力。
- 维护已移除范围不变。本路线不恢复本机协作或独立 JSON Path 提取器，也不把 `it-tools-template` 变成运行依赖。

## 5. 验收与回滚

- 插件 API 设计须先于试点实现，并定义稳定身份、API 版本、入口、能力、设置、生命周期、取消、错误和资源上限。
- 试点必须使用现有能力，不借插件试点增加未说明的业务功能。
- 每个迁移切片均需保留原有数据和行为，并具备单独回滚范围。
- UI、服务集成和多平台构建分别记录对应证据；一个插件的通过记录不替代其他插件的验证。
- 如果插件接口无法维持既有功能合同，先停在设计阶段修正边界，不扩大迁移范围。
