# Ramag Platform 主线路线：功能冻结与维护

> 状态：现行路线
> 更新日期：2026-10-24
> 执行入口：[01-development-plan.md](01-development-plan.md)
> 设计边界：[24-cross-project-capability-matrix.md](24-cross-project-capability-matrix.md)

## 1. 路线结论

Ramag 保留当前工具箱中的全部现有功能，移除本机协作和 JSON Path 提取器。后续路线从
“扩展功能”切换为“维护已有能力”。数据库、Redis、MongoDB、API、Kafka、MQTT、Git、SSH、
对象存储、容器、剪贴板、系统监控、更新、插件宿主和 GPUI Shell 都继续维护。

`it-tools-template` 继续独立承担自己的 Web、PWA、Electron 和通用工具工作台。两个项目
可以提供相同场景的不同实现，但不存在进程调用、代码依赖或接口依赖。

## 2. 阶段路线

### 阶段 A：完成范围收口

移除两个指定工具的 crate、领域模型、应用服务、存储表、注册、窗口入口、脚本和文档引用。
保留 API 工作台内部的 JSON Path 变量和断言逻辑。完成后，工具目录和默认窗口不再显示两个
入口。

### 阶段 B：现有功能维护

按用户反馈和可复现证据处理缺陷、崩溃、性能、资源、取消、权限、兼容性和数据安全问题。
维护任务按一个可验收切片执行，并保持现有工具的功能边界。

### 阶段 C：UI 与发布维护

持续检查 GPUI Shell、首页、工具页、设置、响应式布局和错误反馈。维护三平台构建、安装包、
更新和发布说明。真实窗口、headless、服务集成和发布资产分别记录证据。

## 4. 维护任务的停止条件

遇到以下情况时停止扩大范围，并先补充证据或更新计划：

- 问题无法在当前功能边界内复现或验证。
- 修复会改变现有工具的用户流程、数据格式或外部协议。
- 需要新增工具入口、后台服务、跨项目调用或新的权限能力。
- 维护工作会重新引入本机协作或 JSON Path 提取器。

## 5. 质量要求

每个维护切片先检查工作区和相关文档，再实现、测试、记录证据并提交。Rust 变更至少运行
格式检查、严格 Clippy、受影响测试和完整 `ramag-bin` 构建；UI 变更把真实窗口证据与
headless 证据分开。协议和数据库集成只使用本机服务或本机 Docker。
