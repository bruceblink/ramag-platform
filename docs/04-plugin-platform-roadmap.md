# Ramag Platform 插件化平台开发计划

> 适用项目：`bruceblink/ramag-platform`。本路线只约束当前独立下游项目的插件平台演进，不代表 `tools-rs/ramag` 已接受或实现这些接口。
>
> 当前状态：P0-A 接口模型、静态工具注册适配、P0-B 生命周期、`PLAT-003` 平台 UI 诊断和 `P0-C-1` 能力授权检查已完成；静态插件开发手册见 [`plugin-development-guide.md`](plugin-development-guide.md)。P0-C 的设置命名空间、迁移和秘密存储接口尚未实现；当前不支持第三方动态插件、插件市场或不受信任代码加载。桌面端明确禁止 WebView，后续优先建设原生 GPUI 标准工具入口和第一方工具目录。

## 术语与命名规则

| 名称 | English / Acronym | 本计划中的职责 | 不表示什么 |
|---|---|---|---|
| 平台底座 | Platform Core | 提供窗口、主题、导航、生命周期、配置和共享服务 | 不包含某个数据库或消息系统的业务实现 |
| 工具插件 | Tool Plugin | 通过稳定接口向平台注册入口、视图、能力和设置 | 不表示任意动态代码都能直接加载 |
| 插件清单 | Plugin Manifest | 描述插件身份、版本、兼容范围、权限和入口 | 不表示已执行插件代码或已授予全部权限 |
| 插件宿主 | Plugin Host | 负责发现、校验、加载、隔离和卸载插件 | 不表示业务服务或远程插件市场 |
| 插件能力 | Plugin Capability | 插件向平台声明并按需使用的受控服务 | 不表示插件可以访问任意文件、网络或进程 |
| 静态插件 | Built-in Plugin | 编译进主程序、通过 Rust 接口注册的工具 | 不表示未来动态插件格式已经稳定 |
| 动态插件 | Dynamic Plugin | 在运行时从外部包加载的插件 | 不表示第一阶段必须实现动态 ABI |
| 插件 API | Plugin API | 平台与插件之间经过版本管理的接口集合 | 不等同于内部 crate 之间可随意变化的实现 API |
| 扩展宿主进程 | Extension Host Process | VS Code 中承载扩展代码的独立运行进程 | 不表示 Ramag 的主窗口进程或业务服务 |
| 贡献点 | Contribution Point | 插件清单声明的命令、菜单、视图、设置等平台入口 | 不表示插件可以直接修改宿主内部 UI |
| 外部插件进程 | Out-of-process Plugin | Ramag 未来通过 IPC 接入的独立插件进程 | 不表示已经实现第三方插件加载 |
| 受限插件 | Sandboxed Plugin | 在受限运行环境中执行的解析、转换或计算插件 | 不表示可以安全承载任意系统权限 |
| 原生工具插件 | Native Tool Plugin | 通过 Rust 逻辑和 GPUI 视图接入桌面宿主的插件 | 不表示可以嵌入 WebView 或直接持有宿主窗口对象 |
| 标准工具入口 | Standard Tool Entry | 由平台统一渲染输入、输出、复制、错误和快捷键的轻量入口 | 不表示复杂工作台必须使用统一表单 |
| 计算核心 | Compute Core | 不依赖 GPUI 的解析、转换、校验或计算模块 | 不表示可以访问凭据、数据库或任意文件 |
| 第一方工具目录 | First-party Catalog | 由项目维护、审查并随版本发布的工具清单 | 不表示第三方市场或动态加载已经开放 |
| WebView | Embedded Web View | 被本项目明确排除的桌面网页承载方式 | 不表示 Web 端的 WASM 计算适配 |

## 目标与边界

当前 Ramag 已具备平台化雏形：`ramag-app` 提供 `Tool` 与 `ToolRegistry`，`ramag-ui` 提供 `ActivityBar`、`Shell` 和共享 UI，各工具位于独立 `ramag-tool-*` crate。后续以这些能力为基础，把“新增一个工具”从主程序装配细节中逐步解耦。

本阶段目标：

1. 保持现有数据库、Kafka、Redis、MongoDB、VCS、SSH、对象存储、剪贴板和系统监控行为不变。
2. 明确平台底座、静态插件和未来动态插件的责任边界，避免过早引入不稳定的跨平台 ABI。
3. 先完成稳定的插件描述、注册和生命周期接口，再评估动态加载、权限隔离和插件分发。
4. 每个阶段都有可运行的静态插件和 headless UI 验收，不以“目录能被扫描”作为完成标准。
5. 桌面插件界面全部使用原生 GPUI；WebView、嵌入式浏览器和 Vue 页面直装桌面的方案不进入实现或验收范围。
6. 轻量工具复用不依赖 GPUI 的计算核心；Web 端可以选择 WASM 适配，桌面端直接调用 Rust 核心。
7. 一个插件包可以包含多个稳定工具入口；插件包负责版本和生命周期，入口负责自己的元数据、平台支持和权限声明。

暂不纳入：远程插件市场、第三方不受信任代码的进程沙箱、跨语言动态 ABI、自动升级插件、敏感数据自动同步、Schema Registry、Kafka Connect 和其他大型业务模块。

## VS Code 与 Zed 的扩展模型对比

两者都把“插件描述”和“宿主运行时”分开，但重点不同：VS Code 优先解决大型生态中的贡献点、激活条件和扩展宿主进程；Zed 优先解决 Rust 桌面应用中的原生能力复用、WASM 运行和 capability 边界。Ramag 应分别借鉴，不应把两套机制直接拼接。

| 维度 | VS Code | Zed | Ramag 适配决定 |
|---|---|---|---|
| 扩展实现 | 以 JavaScript/TypeScript 扩展和 `package.json` 清单为主；Web 场景使用受限的 Web Extension 运行方式 | 以 Rust 扩展和 WebAssembly 为重要运行方式，扩展通常围绕 `extension.toml` 与扩展仓库组织 | 桌面内置工具保留 Rust/GPUI；纯计算逻辑可为 Web 编译 WASM；桌面不使用 WebView |
| 宿主边界 | UI/主进程与 Extension Host 分离；本地、远程和 Web 扩展的宿主位置不同 | 宿主加载扩展 WASM，并通过扩展 API 提供受控能力 | `ramag-bin`/`ramag-ui` 继续拥有窗口和 Shell；外部插件不得直接持有 `Shell`、`AnyView` 或 GPUI Context；标准工具由宿主渲染 |
| 贡献点 | 命令、菜单、视图、语言、调试器、配置等由清单声明，宿主渲染或调度 | 按扩展类别提供语言服务、语法、主题等扩展入口 | 第一阶段只抽象工具入口、命令、设置和通知；表格、树和复杂视图逐步增加 |
| 命令与配置 | 命令通过命令注册和激活条件进入宿主；配置通过声明的 configuration contribution 暴露 | 扩展 API 提供与编辑器能力相关的配置和服务 | 命令使用稳定字符串 ID；设置使用插件独立命名空间和设置模式，不能直接读全局配置 |
| 权限 | 不是通用的逐项 capability 授权模型；Workspace Trust、Restricted Mode 和扩展类型会限制部分行为 | 通过 capability 思路收敛扩展对宿主和系统能力的访问 | 所有新增能力都显式声明、授权并在 `PluginContext` 每次调用时检查，默认拒绝高风险能力 |
| 生命周期 | 发现清单 → 根据激活事件启动 Extension Host 中的扩展 → 注册贡献点 → 停用或重启宿主 | 宿主加载扩展并调用扩展 API；扩展构建和加载失败需可诊断 | 统一为发现、校验、注册、激活、就绪、停用、卸载；单个失败不能阻塞其他工具 |
| 兼容性 | 扩展 API 与产品版本分开，manifest/贡献点是生态兼容基础 | 扩展 API、Rust/WASM 构建工具链和宿主版本共同影响兼容性 | `ramag.plugin.v1` 与插件自身版本分离；内部 Rust 类型不作为长期外部 ABI |
| 市场与信任 | 集中式 Marketplace、发布者身份和平台审核形成发现与信任入口，但不等于插件沙箱 | 更接近扩展仓库/目录与构建加载，信任更多依赖来源、源码和宿主能力限制 | 初期不做远程市场；先支持内置插件。动态插件必须先完成来源、签名、权限确认、安装回滚和审计设计 |

### 对 Ramag 的关键借鉴

VS Code 的核心借鉴是“清单描述贡献点，宿主负责生命周期和 UI 组合”。这适合 Ramag 的 `ToolRegistry`、Activity Bar 和 Shell，但不能把 GPUI 内部对象变成公开接口。

Zed 的核心借鉴是“按扩展能力选择 Rust/WASM 运行方式，并让宿主能力有明确边界”。这适合 Ramag 的解析、转换、过滤和校验逻辑；涉及数据库连接、SSH、凭据或系统进程的插件，仍应先采用受控 API，不能因为 WASM 存在就授予任意系统能力。

## 结合当前代码的适配方案

当前实现仍是编译期静态装配，证据和后续边界如下：

| 当前证据 | 现状 | 插件化适配 |
|---|---|---|
| `crates/ramag-domain/src/traits/tool.rs:6`、`:35` | `ToolMeta` 与 `Tool` trait 提供工具元数据和工具抽象 | 增加与业务实现分离的 `PluginDescriptor`、API 版本和能力声明 |
| `crates/ramag-app/src/tool_registry.rs:18`、`:22` | `ToolRegistry` 管理工具注册、查找、顺序和隐藏状态 | 保留现有注册行为，增加来源、状态、冲突和失败诊断 |
| `crates/ramag-ui/src/shell.rs:17`、`:221` | `Shell` 保存统一窗口状态，`register_tool_view` 接收 GPUI `AnyView` | 仅内置插件使用原生视图；外部插件提交结构化贡献点或独立窗口消息 |
| `crates/ramag-bin/src/composition.rs:63` | `build_tool_registry` 在入口侧创建并组装注册表 | 第一阶段包装为静态插件注册入口，不复制现有工具实例或业务状态 |
| `crates/ramag-bin/src/windows.rs:234-246` | 主窗口显式创建并注册数据库、Kafka、VCS、剪贴板、SSH、对象存储和系统工具视图 | 保留该装配路径作为内置插件适配样例；动态发现另行接入，不混入业务工具改造 |
| `docs/architecture.md:18-40`、`:196-254` | `ramag-tool-*` 是独立 crate，但由 `ramag-bin` 负责组合 | 将 crate 边界视为内置插件边界，不把 crate 边界误认为稳定的第三方 ABI |

推荐的调用关系是：

```text
Plugin Manifest -> validator -> Plugin Registry -> Shell contribution model
                                      |
                 +--------------------+--------------------+
                 |                                         |
          Built-in Plugin                          External Plugin Process
          Rust + GPUI                               versioned IPC
                 |                                         |
                 +--------------------+--------------------+
                                      v
                              Plugin Context
                  storage / notification / task / command
```

`ToolRegistry` 仍是工具入口登记组件，不升级为万能服务容器；`Shell` 仍是窗口和导航组件，不升级为插件可以任意调用的对象；业务 driver 和 use case 仍由各自的 crate 负责。插件宿主只负责把受控贡献转换为平台可用的入口。

标准工具入口的装配应遵循以下边界：

1. 插件描述输入、输出、校验、取消和资源上限；平台负责用 GPUI 共享组件渲染表单、结果、复制、错误和快捷键。
2. 插件包可以提供多个入口，但入口 ID 必须独立稳定；任一入口冲突或描述非法时，整个插件包注册失败并回滚。
3. Activity Bar 只登记元数据；视图和重计算任务在用户打开入口后按需创建，关闭入口时取消或回收任务。
4. 复杂数据库、API、Git、SSH 和容器工作台继续作为可信 Rust/GPUI 专用插件，不被强行转换为标准表单。

## 命令、配置、权限与生命周期的统一接口

### 命令和贡献点

插件清单只声明稳定的字符串 ID，例如 `example.open`；宿主负责去重、排序、显示和调度。命令请求必须携带插件 ID、请求 ID、API 版本和有界 payload，返回结果或可诊断错误。菜单、Activity Bar 入口、设置页和通知都使用同样的贡献点校验流程。

### 配置和存储

插件配置分为清单中的设置模式、插件专属命名空间和运行时设置快照。平台负责类型检查、大小限制、版本迁移、备份和原子写入；敏感值只能通过平台秘密存储访问。插件不能读取 Ramag 全局配置、其他插件命名空间或内部 SQLite 文件。

### 权限和进程边界

第一阶段仅允许 `ui.entry`、`ui.notification`、`storage.plugin` 和 `task.scoped`。网络、任意文件系统、子进程、系统密钥环和任意数据库连接不作为默认权限。进程外插件必须通过握手协商 API 版本、能力和消息上限，宿主不能把令牌、完整连接配置或未经筛选的环境变量传给插件。

### 生命周期和崩溃恢复

插件按“发现 → 校验 → 注册 → 激活 → 就绪 → 停用 → 卸载”推进。初始化失败只回滚当前插件；外部插件崩溃时，宿主记录阶段和有界错误摘要，回收 IPC 资源并限制自动重启次数。卸载后，插件持有的上下文必须拒绝迟到调用，其他工具继续可用。

## 插件设置设计

插件设置不是把任意 JSON 直接写入全局配置，而是由四层组成：

1. **插件清单**：只声明插件身份、发布版本、插件 API 版本、入口元数据、设置模式和所需能力；清单是输入数据，不能直接改变运行时权限。
2. **设置模式**：描述设置键、类型、默认值、是否敏感、范围和可选项。第一阶段只允许布尔、整数、有限长度字符串、枚举和有限长度字符串列表，不支持任意嵌套对象或可执行表达式。
3. **插件设置存储**：每个插件使用独立命名空间 `plugin.<plugin-id>.*`；平台负责校验、迁移、备份和原子写入，插件不能读取其他插件的设置。
4. **运行时设置快照**：插件只能读取经过校验的当前快照；设置变更先生成新快照，验证成功后再通知插件。失败时保留旧快照并显示有界错误。

设置生命周期固定为：读取清单 → 校验清单 → 读取命名空间 → 按版本迁移 → 校验模式 → 生成快照 → 初始化插件。迁移必须是有界、可重复和失败可恢复的函数；迁移失败不得覆盖原始数据，也不得启动插件。

敏感设置只允许通过平台提供的受控秘密存储读写，普通插件设置和日志中不得出现明文秘密。插件清单不得声明“读取全部设置”“写入任意路径”或等价的通配能力。

## 权限与生命周期模型

权限分为声明、授予和运行时检查三个状态：

| 阶段 | 负责组件 | 规则 |
|---|---|---|
| 声明 | 插件清单校验器 | 只接受平台已知的能力名称，拒绝未知或重复能力 |
| 授予 | 平台设置/策略层 | 默认拒绝高风险能力；用户或发行版策略明确授予后才可使用 |
| 检查 | `PluginContext` | 每次调用能力都检查插件身份、当前授权和生命周期状态 |

第一阶段的能力集合固定为 `ui.entry`、`ui.notification`、`storage.plugin` 和 `task.scoped`。文件系统、网络、子进程、系统密钥环和任意数据库连接暂不作为默认能力；未来增加能力必须同时补充威胁模型、权限说明和测试。

桌面端插件 UI 只允许使用宿主提供的 GPUI 组件或经过审核的原生 GPUI 视图。WebView、嵌入式浏览器和插件自行创建的外部窗口不属于默认能力；Web 端的 WASM 适配只运行计算核心，不改变桌面权限边界。

插件状态为 `Discovered`、`Validated`、`Enabled`、`Failed`、`Disabled` 和 `Unloaded`。状态只能沿合法方向变化：清单或兼容性校验失败进入 `Failed`，用户禁用进入 `Disabled`，初始化失败时只回滚当前插件并保留其他插件，关闭后进入 `Unloaded`。已卸载插件持有的上下文必须拒绝迟到调用。

## 安装、升级和卸载边界

第一阶段只支持编译期静态插件，不扫描外部目录、不执行外部代码、不自动升级插件。未来动态插件若进入 P4，必须先完成包格式、签名、来源、兼容性、权限确认、原子安装、回滚和删除残留文件的设计。

静态插件升级随主程序发布，插件 API 主版本不兼容时在编译或启动阶段明确失败；插件次版本向后兼容。插件设置迁移与主程序升级分离，迁移失败可回退到上一份设置快照。卸载动态插件时只能删除其受平台管理的目录和设置命名空间，不能删除用户选择的外部数据。

## 实施阶段

### P0：接口和装配边界

新增平台侧 `PluginDescriptor`、`PluginId`、API 版本、能力声明、设置模式和注册错误类型；把现有 `ToolRegistry` 注册流程包装为静态插件注册入口。生产代码必须继续使用当前工具实例，不能复制业务状态。验收：所有现有工具注册结果不变，重复 ID、空 ID、非法版本、冲突入口、未知能力和非法设置模式有明确错误或诊断，相关单元测试通过。

### P1：静态插件生命周期

为静态插件定义 `initialize`、`register`、`shutdown` 的生命周期顺序和失败行为；平台负责按逆序关闭已成功初始化的插件。插件只能通过平台提供的受控上下文访问设置、通知、窗口和任务服务。验收：初始化失败不会阻塞其他插件，关闭过程不泄漏任务或重复释放，启动和关闭状态有测试覆盖。

### P2：插件设置和权限声明

定义插件清单中的设置模式、命名空间、迁移策略和最小权限集合。默认拒绝未声明的能力；现有工具权限逐项登记，不改变用户已有配置。验收：未知权限、越权命名空间、非法类型、超限值和迁移失败均被拒绝并给出可读诊断，插件设置不会覆盖其他插件，版本升级和损坏配置可恢复。

### P3：平台 UI 与插件诊断

将插件加载失败、禁用、版本不兼容和能力缺失统一显示在平台状态区域；Activity Bar 和设置页只展示成功注册且可用的插件。验收：长错误文案、空插件列表、禁用状态和重试/恢复入口在 360/1024/1440 headless 窗口内可见且不越界。

### P4：动态插件可行性评估

在静态插件 API 稳定并完成安全评审后，单独进行动态加载技术验证。优先比较进程外协议、WASM/WASI 和平台原生 ABI 的兼容性、崩溃隔离、签名验证、性能和升级回滚成本。只有形成决策记录和最小安全模型后，才决定是否实现动态插件。

### PLAT-004：多入口原生插件与标准工具入口

在 `P0-C` 完成后，把一个插件包与多个工具入口分开建模，并提供有限的输入、输出、校验、取消和资源预算描述。入口由 `ramag-ui` 统一渲染；复杂工作台继续使用可信的专用 GPUI 视图。验收覆盖入口冲突、非法描述、窄窗口布局、按需打开和错误回退。

### PLAT-005：按需激活与资源预算

把入口登记与视图创建分离，未打开的工具不创建视图；插件任务与生命周期绑定，关闭、禁用和卸载时取消或等待任务。验收记录首次打开耗时、空闲内存、任务取消、输入上限、结果上限和恢复失败行为。

### TOOL-MIG-001：首个 IT Tools 原生迁移样例

选择 JSON Path 提取器作为首个标准工具样例，将解析和查询逻辑迁入无 GPUI 的 Rust 计算核心，再接入原生 GPUI 输入/输出界面。Web 端是否使用 WASM 单独评估，不能以桌面 WebView 作为复用方案。

### DUAL-CORE-001：双端计算核心适配

为已迁移的纯计算核心建立 Web/WASM 适配和共享测试样例。桌面端直接调用 Rust 核心，Web 端按需加载 WASM；平台目录记录每个入口的 `desktop`、`web` 支持状态和限制。

### CATALOG-001 与 COLLAB-001：第一方目录和本机优先协作

第一方目录先服务内置或已审查插件，记录版本、能力、平台、数据处理和验收状态。协作层先实现用户明确选择的文档或结果共享，使用本机加密存储和可审计的同步记录；密码、JWT 密钥、连接配置和原始业务数据默认禁止自动同步。

## 关键设计约束

- 插件 ID、API 版本和权限名称必须是稳定、可校验且可记录的字符串；不得使用显示名称作为身份。
- 插件不能直接持有或修改 `ToolRegistry`、`Shell` 内部状态；通过明确的上下文接口完成注册和通知。
- 注册失败必须保留其他插件可用性，并记录插件 ID、阶段和有界错误摘要，不记录密码、令牌或完整连接配置。
- 插件任务必须绑定插件生命周期；关闭插件时取消或等待其任务，并拒绝迟到状态更新。
- 插件 API 先服务 Rust 静态插件；动态插件 ABI 另行版本化，不把内部 Rust 类型直接暴露为长期 ABI。
- 桌面端插件 UI 必须使用 GPUI；WebView 不属于可选实现路径。
- 纯计算核心与 UI、凭据、网络和数据库访问分离，以便桌面原生调用并在 Web 端选择性编译 WASM。
- 一个插件包可以包含多个入口，但每个入口必须有独立稳定 ID、平台标识和能力声明。
- 每个独立阶段单独提交、测试和推送；未通过目标测试、workspace Clippy、格式和源文件大小检查的变更不得提交。
